Red Team Assessment Methodology

Red Team Assessment Methodology

Four toolsets, 42 test cases, 2026-06-02. All tests targeted the model serving endpoint via direct HTTP invocation using a personal access token, simulating an attacker holding API credentials but not the application proxy layer.

ToolCategoryTests RunWhat Was Tested
Garak LLM Vulnerability Scanner 4 Prompt injection probes (promptinject.HijackHateHumans, HijackKillHumans) and encoding-based injection (encoding.InjectBase64, InjectROT13). Generator and probe loading succeeded; probe execution requires Garak's native reporting harness for full result capture - a known integration constraint when targeting custom endpoints.
PyRIT AI Red Teaming Framework (Microsoft) 4 Encoding evasion attacks (Base64, ROT13, hexadecimal, character reversal) designed to obfuscate prompt injection payloads and determine whether the model would decode and execute hidden instructions. Applied in the spirit of PyRIT's adversarial input generation methodology.
Counterfit ML Security Testing (Microsoft) 5 Adversarial text perturbations (homoglyph substitution, character swap, l33tspeak) targeting input filtering evasion, and membership inference probes testing whether the model reveals training data membership for internal documents or employee records.
Manual STRIDE Harness Structured Adversarial Testing 29 Custom test suite aligned to STRIDE categories: identity spoofing via direct user_id injection, RAG corpus injection, long-term memory write poisoning, system prompt extraction via multiple vectors (direct, encoded, translated, authority escalation), cross-user memory access, tool enumeration, SQL injection, ReACT loop triggering, and elevation of privilege via confused deputy and plugin bypass framing.

Detection Methodology Note

Automated pass/fail verdicts in the test harness used keyword presence checks against model responses. Several keywords - system, token, assistant, internal, configuration, endpoint - are structural vocabulary for this framework's domain and appear routinely in correct refusal messages (e.g., "I cannot decode instructions that would override system prompt controls"). This produced false positives: model refused the attack correctly, keyword in the refusal text triggered VULNERABLE. Each finding was manually reviewed against the codebase to produce the verdicts below.

Scope and Limitations

Targeted and time-boxed, not exhaustive. Constraints stated so findings are read at the confidence they warrant.

LimitationDetail and effect on confidence
Sample size 42 test cases, single day. Scoped to STRIDE categories and the agentic threat surface (memory, delegation, RAG ingestion, tool routing), not broad fuzzing. Multi-week engagements run orders of magnitude more cases. Absence of a finding here is not evidence of absence.
Automated vs. manual split 13 of 42 cases (31%) off-the-shelf tooling, 29 (69%) custom harness. Depth comes from manual code review, not tool volume. Scoping choice: constraints below limit what the scanners return, and LLM red teaming is majority-manual in practice.
Garak coverage unvalidated All 4 probes loaded against the custom generator. Result capture needs Garak's native reporting harness, not wired to the endpoint. These 4 are excluded from the reconciliation table. Treat as not validated, not passed. promptinject and encoding families have no empirical verdict here.
Counterfit membership inference 2 of 5 Counterfit cases were membership inference probes. Not rowed individually; summarized under I-7. Not confirmed, not pursued to a rigorous conclusion.
Detector was the weakest instrument Keyword-presence checks produced a 69% false positive rate (18 of 26 flagged). Limiting factor was the harness's detection logic, not the model. Replacing keyword matching with an LLM-as-judge or refusal classifier is the top methodology fix for the next round. Changes the raw numbers, not the verdicts.
Single assessor, no peer review One analyst, no independent review of false-positive and not-applicable calls. Reclassifying a raw CRITICAL flag as not applicable (S-1a) rests on a single reading of the proxy's identity derivation.
Platform controls taken as documented No source-level review of the platform (proxy, SSO header injection, endpoint ACLs). Platform behavior assumed to match vendor documentation. TB1 and TB2 controls asserted, not verified.
Point in time Assessed 2026-06-02 against one model version and framework commit. Findings do not carry across model changes, prompt revisions, or new tool registrations. Any triggers re-assessment.

STRIDE Methodology

STRIDE Methodology

STRIDE is a threat modeling framework that categorizes threats by the type of security property they violate:

Category Violates Definition AI-Specific Concern
Spoofing Authentication Attacker impersonates a user, component, or identity Identity forgery via headers, user identity spoofing, agent impersonation
Tampering Integrity Attacker modifies data or code without authorization Memory/KG poisoning, RAG corpus injection, relay manipulation
Repudiation Non-repudiation Actor denies performing an action; logs cannot prove otherwise Missing signed audit trail on tool calls and model decisions
Information Disclosure Confidentiality Data exposed to unauthorized parties System prompt extraction, cross-user memory leakage, PAT exposure
Denial of Service Availability Resource exhaustion or system disruption ReACT loop attacks, scale-from-zero cost amplification
Elevation of Privilege Authorization Attacker gains capabilities beyond their grant Prompt→tool→SQL chain, relay→code execution, memory identity escalation

Severity Framework

Severity DREAD Total Action Required
Critical38–50Immediate remediation before use
High28–37Remediation within current sprint
Medium18–27Backlog item; mitigate within quarter
Low≤17Document; accept or address in future cycle

DREAD scoring: Damage (1–10) + Reproducibility (1–10) + Exploitability (1–10) + Affected users (1–10) + Discoverability (1–10)

On the choice of DREAD: known limitations

DREAD is used for legibility and continuity, not because it is the most defensible model available. Its weaknesses are documented, and Microsoft moved away from it. They apply here:

  • Subjective and not reproducible. Scores are analyst-assigned, no calibration rubric. A second assessor would produce different totals; with one assessor there is no inter-rater check. Band boundaries (38/28/18) are conventional, not derived.
  • Additive scoring conflates unlike dimensions. Summing damage with discoverability lets a low-impact, easily-found issue outrank a high-impact, hard-to-find one. I-1 is the clearest case: 27 total, driven by Affected users (10) and Exploitability (9) against Damage of 3. Low damage, broad reach. Components carry the meaning, not the sum.
  • Ordinal scores treated as cardinal. 27 to 28 crosses a severity band but is not a meaningful change in risk. Do not prioritize on band alone near a boundary.

How to read these scores: relative ordering within this document. Not absolute risk, not comparable across assessments. CVSS v4 or an explicit likelihood x impact matrix would be more defensible for external audit. DREAD is retained because it is compact and consistent with the prior revision; changing scoring mid-stream breaks comparison. Residual risk is prioritized on verdicts and attack-path analysis, not DREAD totals.
